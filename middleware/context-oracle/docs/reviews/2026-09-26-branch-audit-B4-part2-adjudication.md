### E-1
**Ruling:** Both reviews say `replace`; the second opinion's two corrections are upheld, and the exit-128 defect is upheld with a sharper root cause than either review states. (a) The exit-128 → "watermark object is gone" mapping is wrong, as both reviews found: 128 is git's generic fatal status, and a purge of every history table on that status is a data-destroying fallback on an ambiguous signal. (b) The second opinion's Correction 1 is upheld: both horizons (commit-count and time) are tested only against the commits in the pass's own `<range>`, so on an incremental pass neither excludes anything; the plan states the rule as if it held in general. The recency dampener in Step 16 lowers old pairs' confidence but never excludes them, and `change_count` denominators are never aged, so the stored corpus is horizon-capped only at a full mine. (c) The second opinion's Correction 2 is upheld and made a root-cause rule rather than a special case: exit 1 from `--is-ancestor` does not mean "history rewritten". It means "the stored commit is not reachable from `HEAD`", which is equally true after an ordinary branch switch. git's own definition of a rewrite is a **non-fast-forward update of a ref**: git-push(1) — "When an update changes a branch (or more in general, a ref) that used to point at commit A to point at another commit B, it is called a fast-forward update if and only if B is a descendant of A." A rewrite is therefore a property of *one ref moving*, and the watermark must be keyed to the ref it was mined from (`git symbolic-ref -q HEAD`, or the literal detached marker when that exits 1), not to a bare commit compared against whatever `HEAD` currently is. With the key stored, the three cases separate by git's documented semantics: **same ref, watermark is an ancestor of the tip → fast-forward → incremental pass**; **same ref, watermark exists (`git cat-file -e` exit 0) but is not an ancestor (exit 1) → non-fast-forward update of the mined ref → history rewritten**; **same ref, watermark object absent (`git cat-file -e` exit 1) → the old tip was rewritten away and then pruned → also a rewrite** (an object no ref reaches cannot be an ancestor of the tip); **different ref → a checkout, not a rewrite** — the stored aggregate describes another line of history, which under the aggregate storage model (no per-commit touched-file lists outside `labelled_touches`) still needs a purge and re-mine, but the diagnostic must say `branch_changed`-class (`{oldRef, newRef, oldWatermark, newHead}`), not `history_rewritten`, and the re-mine's cost (a full chunked pass with `mining_in_progress` silencing the history genres, and the lock hold batch 3 measured) must be stated; **any `merge-base` or `cat-file` status outside {0, 1} → a git fault (`miner_git_failed`-class), no purge**, per the fail-fast rule. Executed here: an amend on the same branch exits 1 with the old object still present (the reflog keeps it), a branch switch also exits 1, and 128 appears only after `reflog expire` + `prune` or for a bogus hash — so the plan's two-status rule conflates the common rewrite with the common checkout and reserves for "object gone" a status that in practice means "git failed". The first audit's other items (inherited B3b E-7 yield, B3b E-14 lexicon, B3a E-7 terminology, B3b E-22 projection, unsourced `365.25`, the never-both-labels rule kept) stand as written.

### E-3
**Ruling:** Both reviews say `replace`; the second opinion's disagreement on the `.js`→`.ts` substitution is upheld. The first audit lists the substitution among the parts to keep and calls it "the handbook's rule". The plan's text is an ordered list ending "first existing file wins", so the written `.js` path is tried before its `.ts` source, and `.d.ts` is never tried. The handbook's rule is the reverse: TypeScript first looks for the TypeScript implementation or declaration file with the analogous extension, and does so regardless of the specifier written. In a repository committing both `util.ts` and a built or shim `util.js`, the plan resolves `./util.js` to `util.js` while the compiler resolves it to `util.ts`; the import edge, Reuse's counts, Orientation's hub degree and the unresolved share all follow the wrong file. So the substitution cannot be kept as written; its order must follow the handbook (TypeScript file first, `.d.ts` included). The rest of the first audit stands: the "NodeNext" label mis-attributes the union (the handbook restricts extensionless relative paths under `nodenext` to `require`), the workspace inheritance (B3b E-15), the Python `src`-layout defect (PyPA: the src layout requires installation to run its code — `sys.path`, not the repository root), and the parse-failure catch-all needing a fault class and a per-pass bound. The second opinion's caution is also upheld: the "about 75 crashes" figure from the later Step 15 review is hindsight outside the as-of-commit judgment; the fail-fast standard alone carries the point, and the correction does not depend on that figure.
**Evidence:**
- The plan's order: [[middleware/context-oracle/docs/plans/plan-phase-a.md@2331baf:L3416-L3420]] "TypeScript `moduleResolution: NodeNext` for relative specifiers (`./`, `../`): the written path if it exists; a `.js`/`.jsx`/ `.mjs`/`.cjs` specifier also tries its source `.ts`/`.tsx`/`.mts`/`.cts`; an extensionless one tries `.ts`, `.tsx`, `.js`, `.jsx`, then `/index.` + those; first existing file wins"
- The handbook's order and its independence from the specifier: [[https://www.typescriptlang.org/docs/handbook/modules/reference.html]] "TypeScript will first try to find a TypeScript implementation file or type declaration file with the same name and analagous file extension" and [[https://www.typescriptlang.org/docs/handbook/modules/reference.html]] "Note that this behavior is independent of the actual module specifier written in the import." and [[https://www.typescriptlang.org/docs/handbook/modules/reference.html]] "TypeScript can resolve to a .ts or .d.ts file even if the module specifier explicitly uses a .js file extension"

**Final verdict:** replace

### E-15
**Ruling:** The second opinion's overturn (`keep` → `replace`) is upheld. The first audit's statement that no batch-3 `replace` is inherited by this step's own text is false.
