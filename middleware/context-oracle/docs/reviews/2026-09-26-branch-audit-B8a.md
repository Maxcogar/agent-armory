### E-5
**Units:** B8-52-37ea382-docs/plans/plan-phase-a.md#h17
**Question:** For the `init` verb, a refused index run makes `init` finish every other item, print that an index run is in progress, and exit 0, "the running pass will produce the index". Is exit 0 with that promise backed?
**Facts:**
- The hunk [[middleware/context-oracle/docs/plans/plan-phase-a.md@37ea382:L6127-L6130]] "`{refused: 'reindex_locked'}` (another index run holds the claim), `init` still completes every other item, prints that an index run is already in progress and when it started (the claim's `reindex_started_at`), and exits 0: the running pass will produce the index."
- "Held" means only that a pid recorded in the row is alive [[middleware/context-oracle/docs/plans/plan-phase-a.md@37ea382:L3771-L3773]] "treats the claim as held only when that pid is alive (`process.kill(pid, 0)`; `EPERM` counts as alive), and when free or stale writes its own pid and"
- Batch 5 ruling 4 names that mechanism's pid-reuse and `EPERM` cost [[middleware/context-oracle/docs/reviews/2026-09-26-branch-audit-B5-verification.md@HEAD:L127-L128]] "The other is pid reclaim, stating its pid-reuse and `EPERM` cost."
- The `index` verb, for the same condition, exits 75 (E-4) [[middleware/context-oracle/docs/plans/plan-phase-a.md@37ea382:L5714]] "changes nothing, and exits 75 (`EX_TEMPFAIL`, sysexits.h: a temporary failure, try again later);"
- Batch 6 item 9 [[middleware/context-oracle/docs/reviews/2026-09-26-branch-audit-B6-verification.md@HEAD:L149-L150]] "9. **init order** (6a E-23). Hooks are wired before the index, so a failed index leaves them wired. Index first, or unwire on failure."
- Project rule [[middleware/context-oracle/CLAUDE.md@HEAD:L104-L105]] "**1. The owner cannot catch your mistakes.** Never claim something works without having run it"
**Standard:** CLAUDE.md dominating rule 1 (no success claim without the check), Phase A's goal (no output that looks more complete than it is), and fail-fast: a command that did not do its central job reports that, with a non-zero status, rather than predicting that someone else will.
**Reasoning:** (1) `init`'s central job includes "the first index". On a refused run `init` did not index. (2) "The running pass will produce the index" is a prediction about another process: that process may fail, may be incremental from an older state, or may not exist at all — a reused pid reads as live, the cost ruling 4 names. `init` checks none of this. (3) Exit 0 plus "will produce the index" therefore states a success that was not established. (4) The same condition gives `index` exit 75; nothing in the hunk says why `init` should differ. (5) With batch 6 item 9's hooks-first order, a refused `init` leaves hooks wired to a store `init` did not index.
**Alternatives:** (a) `init` reports that the first index was not run by it, names the holder pid and start time, and exits 75 like `index`, so the user re-runs `init` or `index`. (b) `init` waits for the claim to clear (`init` is not the event handler, so "the handler never waits" does not apply), with a bounded wait reported on timeout. (c) The hunk: exit 0 with a prediction. (a) or (b) beat (c) because they report only what `init` observed.
**Consequences:** `177e59f`'s `cli/init.ts` stand-in implements (c) (E-12). Batch 6 item 9 (hooks before index) and batch 4 item 7 (no worktree index into the shared store) apply to the same verb.
**Verdict:** replace — a refused first index makes `init` say the index was not built by this run, with the holder's pid and start time, and exit 75 (or wait for the claim, bounded and reported); drop "the running pass will produce the index".
**Would be wrong if:** the claim could only ever be held by a pass guaranteed to complete a full index of the same checkout (the liveness test cannot establish that).
