## What the revision added beyond round 1: verdict per item

- **(a) `UserPromptSubmit` spawn** — acceptable in principle. The reason (a session already running at the upgrade would otherwise stay silent until its next `SessionStart`) is sound, and the cost is small: [[ran]] `node $A/spawn_probe.mjs` (200 detached `spawn` + `unref` calls, 20 ms apart) → `n=200 p50=2.255 p95=3.973 max=5.615 ms`, against NF-1's 1.5 s. The process count is one per prompt only while the store is pending, and later children exit `reindex_locked` under the 100 ms lock wait; for a one-transaction 003 migration the window is short. The spec has no line bounding per-event work beyond NF-1 and FR-O5 (no idle timers), which a spawn on an event does not breach. The defects are the unbounded case (R2-7: a failed forward migration keeps the store pending and re-spawns on every prompt) and the sections that omit it (R2-8).
- **(b) fixed epoch grid** — R2-5.
- **(c) `reweight_pending`** — crash-safe as written. The marker is written in the pass's first transaction and deleted in the final one with `ref_ts`, `weight_epoch` and `mined_half_life_days`; a retry unions its own `W` with the marker's set, so a commit that a crashed pass mined or re-weighted at another `refTs` or `h` is recomputed; recomputing, not multiplying, makes a repeat write the same values. I checked the three cases by hand: a crashed pass at `refTs1` with a retry at `refTs2` (covered by the floor `min(R0, refTs1)` plus the retry's own `min(R0, refTs2)`), an epoch move in the crashed pass (covered by `'all'`), and a single-transaction pass (the set and clear land in one transaction, so no reader sees the flag). Only the `'all'`/floor merge is unstated (R2-11).
- **(d) composer order** — R2-3.
- **(e) Orientation without hub degree while `mining_in_progress`** — sound engineering: the factor multiplies partial pair counts, which the history genres are already barred from. The gaps are consistency and definition (R2-8).
- **(f) `file_parse` as a table** — acceptable: the SQLite page quoted above says an added `CHECK` column is tested against every existing row, and the table is also sparse (a row only for a file whose last parse was not clean), which a column would not be.
- **(g) 392-extension rule** — R2-4.
- **(h) `reindex.lock` identity check** — R2-9. The method list the design rests on is correct: [[ran]] `node -e "const {DatabaseSync}=require('node:sqlite');console.log(Object.getOwnPropertyNames(DatabaseSync.prototype).join(','))"` → `open,close,prepare,exec,function,location,aggregate,createSession,applyChangeset,enableLoadExtension,loadExtension,constructor`.
