### E-1
**Units:** B7-36-a02adc0-docs/architecture-phase-a.md#h1
**Question:** AD-13 gains three rules — a commit already in `commits` is skipped, the pass's final transaction sets `last_mined_commit` to the `HEAD` mined to (a merge `HEAD` included), and `files` rows whose commit provenance was purged are re-pointed or swept. The commit message and the *Why* attribute the raise to the Step 13 test writer: with `--no-merges` a chunk watermark can never equal a merge `HEAD`, so every history fact reads stale forever under AD-14. Was the raise real, and is the change the correct fix?
**Facts:**
- The prior text kept the watermark per chunk and mined `watermark..HEAD` [[middleware/context-oracle/docs/architecture-phase-a.md@a02adc0:L1499-L1501]] "mine only `watermark..HEAD`, committed in bounded chunks, each chunk advancing the watermark to its own last commit (AD-26)." — this line is unchanged by the hunk.
- The hunk adds the skip and the final watermark [[middleware/context-oracle/docs/architecture-phase-a.md@a02adc0:L1501-L1504]] "**A commit already in `commits` is skipped, never counted again,** so a resumed pass is idempotent whatever order the history's branches interleave in. **The pass's final transaction sets `last_mined_commit` to the `HEAD` it mined to**, including when `HEAD` is a merge."
- Its stated reason [[middleware/context-oracle/docs/architecture-phase-a.md@a02adc0:L1505-L1508]] "the stream excludes merges (`--no-merges`), so a chunk watermark can never equal a merge `HEAD` — every history fact would read stale forever under AD-14's `last_mined_commit ≠ HEAD` rule on a merge-PR repository"
- AD-14's staleness rule [[middleware/context-oracle/docs/architecture-phase-a.md@a02adc0:L1567-L1568]] "a history fact is stale when `schema_meta.last_mined_commit` ≠ `HEAD`"
- The raise is real by git's documentation [[https://git-scm.com/docs/git-log]] "--no-merges Do not print commits with more than one parent." and by execution on a throwaway repository whose `HEAD` is a merge [[ran]] `git log -M -z --numstat --format='%x1e%H' HEAD | tr -cd '\036' | wc -c; git log --no-merges -z --numstat --format='%x1e%H' HEAD | tr -cd '\036' | wc -c` → `5` then `4` (the merge `cb917fe` is the fifth header and is absent from the `--no-merges` stream, so no chunk's newest commit can be it).
- The batch 5 ruling that this design must meet [[middleware/context-oracle/docs/reviews/2026-09-26-branch-audit-B5-verification.md@HEAD:L96-L101]] "The watermark is the `HEAD` resolved once when the pass starts, merge or not. It is keyed to the mined ref (batch 4) and written only in the pass's final transaction. - The next range is `<tip>..<new HEAD>`, or `HEAD --not <tips>`. - A crashed pass re-runs its recorded range and skips hashes already in `commits`."
- The per-chunk watermark the hunk keeps loses commits under clock skew. Throwaway repository `k`: `root` → `p` (dated 2024-03-01) on `main`; `c` (child of `p`, dated 2024-01-15) on `side`; `q` (2024-04-01) on `main`; merge `M`. [[ran]] `git log --no-merges --reverse --format='%h %s' HEAD` → `be509f0 root`, `71ea0b8 c-child-dated-before-p`, `46397dd p`, `2005538 q` (the child `c` streams before its parent `p`); [[ran]] `git log --no-merges --format='%h %s' 71ea0b8..HEAD` → `2005538 q` (a resume from a chunk watermark at `c` never reaches `p`). git documents the default order as date-based [[https://git-scm.com/docs/git-rev-list]] "By default, the commits are shown in reverse chronological order." and only `--date-order`/`--topo-order` promise "Show no parents before all of its children are shown".
- Executed against the built `57bdd4a` code (scratch extraction, `miner.chunk_ms` 0): a store mined to `root`, then an incremental pass stopped after the chunk whose watermark is `c`, then resumed [[ran]] `node mine.mjs <57bdd4a dist> k p.db g.db diag stop:71ea0b8… 0; node mine.mjs … auto 0` → after the stop `"watermark":"71ea0b8","commits":["be509f0","71ea0b8"]`; after the resume `"commitsSeen":1,…,"watermark":"cb917fe","commits":["be509f0","71ea0b8","2005538"],"files":["r:3"],"faults":[]` while the uninterrupted reference gives `"commits":["be509f0","71ea0b8","46397dd","2005538"],"files":["r:4"]`. Commit `p` is lost, `change_count` reads 3 for 4, the watermark reads `HEAD`, and no fault is written. The same run on the `HEAD` build gives the same loss.
- The mined ref is not part of the hunk; batch 4 already required it [[middleware/context-oracle/docs/reviews/2026-09-26-branch-audit-B4-verification.md@HEAD:L104-L105]] "Key the watermark to the mined ref (`git symbolic-ref -q HEAD`, with a detached marker)."
- The record of the raise: the only trace in the repository is the parenthetical *Why* above and the commit message; no test-writer report or STOP text exists under `docs/`. Verified: `git grep -c "test writer" a02adc0 -- middleware/context-oracle/docs` finds the architecture line only.
**Standard:** Batch 5 ruling 1 (quoted above) is the settled design this change must meet. Fail-fast (Shore, *Fail Fast*, IEEE Software 2004) [[https://martinfowler.com/ieeeSoftware/failFast.pdf]] "The program continues working right after an error but fails in strange ways later on." — a watermark that reads fresh while a commit is missing is exactly that. Brief §"The test", clause 5: the change must show why it beats the alternatives.
**Reasoning:** The raise was real: git never emits a merge in a `--no-merges` stream, so a chunk watermark cannot be a merge `HEAD`, and AD-14's rule then reads every history fact stale — executed above. The final-transaction watermark and the already-mined skip are each correct in isolation, and the skip is part of ruling 1. But the hunk keeps the per-chunk watermark and the `watermark..HEAD` resume that ruling 1 replaces, and the retained mechanism has a demonstrated data-loss path: because git's default order is by date, a skewed child can stream before its parent; a crash after that child's chunk leaves the parent outside `watermark..HEAD` for ever, with the watermark at `HEAD` and no fault. The skip cannot repair this (it prevents double counting, not omission). The hunk therefore fixes the merge symptom without adopting the root-cause design (watermark resolved at pass start, written only at pass end, crash re-runs the recorded range). The provenance re-point and sweep rule is sound in itself and is retained. The ruling's "keyed to the mined ref" is also absent.
**Alternatives:** Ruling 1 as written: resolve `HEAD` once, write it only in the final transaction keyed to the mined ref, record the range at pass start, and on a crash re-run that range skipping hashes already in `commits`. It needs no per-chunk watermark, so no clock-skew path exists, and the merge case falls out (the watermark is whatever `HEAD` was). The hunk's design loses to it on the executed skew case.
**Consequences:** Every downstream unit that carries the per-chunk watermark inherits this: e903eda h5 (E-3), 277b0a2 Step 13 text, `cochange.ts` at `57bdd4a` and at `HEAD` (the loss reproduces on both builds). T-13-5/T-13-6 must gain ruling 1's merge-at-boundary and clock-skew cases. AD-13's *Why* text is otherwise accurate and stays as the record of the raise.
**Verdict:** replace — keep the already-mined skip, the final-transaction watermark and the provenance re-point/sweep rule; drop "each chunk advancing the watermark to its own last commit" and the `watermark..HEAD` resume in favour of batch 5 ruling 1 (watermark = `HEAD` resolved at pass start, keyed to the mined ref, written only at pass end; a crash re-runs the recorded range skipping mined hashes), and cite the executed skew case as the reason.
**Would be wrong if:** git's default `git log` order guaranteed parents after children (it does not: only `--date-order`/`--topo-order` do), or the executed resume above had recovered commit `p`.
