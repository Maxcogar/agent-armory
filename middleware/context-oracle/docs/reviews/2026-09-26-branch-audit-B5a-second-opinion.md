### E-10
**Agree/Disagree:** (a) Verdict: **agree**, replace. Both of the first auditor's corrections are needed: the architecture must state the stale-claim rule, and "the handler never waits on it" must be reconciled as batch 3 settled. (b) Reasoning: **partly disagree**, on two points.
1. **Root cause.** The claim row is a root-cause fix for only half of AD-26's lock problem. Taking the check and the claim inside one `BEGIN IMMEDIATE` transaction removes the check-then-act race, and the executed 200/200 shows it. But the claim still uses the lock-file model's stale-marker recovery: a persistent row that outlives its owner, reclaimed by `process.kill(pid, 0)` liveness. A lock whose lifetime is the owner process's removes stale reclaim entirely, which the row does not. A reused pid makes a dead owner's row read as held, and `EPERM` counts as alive, so the claim refuses reindexing until that unrelated process exits. I executed the standard alternative: an SQLite write lock held on a dedicated lock database, which the OS releases when the holder dies, even under `SIGKILL`. The plan compared the claim row only with the `wx` file lock, so brief test 5 (why this beats the alternatives) is unmet for the stale-recovery half. The architecture should either adopt a process-lifetime lock or state the pid-liveness rule with its pid-reuse cost.
2. **Backing.** The first auditor's SQLite quote does not back its point. "An attempt to invoke the BEGIN command within a transaction will fail with an error" is about nested `BEGIN` on one connection, not about one writer across processes. The page's own passages on `BEGIN IMMEDIATE` and single-writer semantics are the backing (quoted below).

### E-18
**Agree/Disagree:** (a) Verdict: **agree**, replace. (b) Reasoning: **agree, with one precision**. I agree on three points:
- **Storage.** "A normalized-token column on `symbols`" cannot serve a prefix query on a name's second token, and `0676431` corrected it to a row per token.
- **Separators.** `_` and `$` silently stop being token characters, a change from the prior FTS tokenizer that no reason covers.
- **The FTS tokenizer.** Which FTS5 tokenizer sits over the pre-normalized tokens is part of the "one tokenizer" decision and is unnamed.
The precision concerns why the FTS tokenizer matters. SQLite documents `unicode61` as the default, with Unicode 6.1 classes and diacritic removal. `ascii` passes every non-ASCII codepoint through as a token character. Only a pass-through tokenizer guarantees that the engine does not re-segment or re-fold the oracle's tokens. The plan's later `tokenize = "ascii"` is that choice, so the architecture should require a pass-through. I did not find a character on which `unicode61` actually re-splits an in-house token: U+A7C1, a letter added after Unicode 6.1, stayed one token under both tokenizers. So the risk is unverified, not shown. It is still a decision the architecture leaves unstated.
**Evidence:**
- [[middleware/context-oracle/docs/architecture-phase-a.md@6cff0ce:L355-L356]] "a normalized-token column on `symbols` and a `path_tokens` table"
- [[middleware/context-oracle/docs/architecture-phase-a.md@6cff0ce:L357-L359]] "split on every non-letter/non-digit (Unicode), NFKD-normalize, drop combining marks, lowercase."
- [[middleware/context-oracle/docs/architecture-phase-a.md@0676431:L355-L358]] "a name such as `Foo::Bar` is two tokens, so a prefix query for `bar` needs a row per token, not one column"
- [[middleware/context-oracle/docs/plans/plan-phase-a.md@2331baf:L2151]] "tokenize = \"unicode61 remove_diacritics 0 tokenchars '_$'\""
