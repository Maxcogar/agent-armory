## The watermark rule (ruled once, applied in H1 E-9, H1 E-16, H2 E-4, H2 E-32)

The half-1 second opinion's rule is adopted as the root-cause correction, reconciled with batch 4's settled ref-keying:

1. The watermark is the tip whose whole reachable set the completed pass mined: the `HEAD` hash resolved once at the pass's start, merge or not, keyed to the mined ref (`git symbolic-ref -q HEAD`, with a detached marker — batch 4 item 1). It is written in the pass's **final** transaction. Chunk transactions write their data and nothing to the watermark.
2. The next incremental range is `<tip>..<HEAD resolved now>` (equivalently `<HEAD> --not <tip>`; for several mined tips, `--not <tip₁> <tip₂> …`). By `gitrevisions`, that excludes each tip and all its ancestors — exactly the mined set — so nothing is streamed twice and nothing unstreamed is excluded.
3. A crashed incremental pass leaves the watermark at the old tip and its committed `commits` rows in place; the next pass runs the same `<old tip>..<HEAD>` range and skips every hash that already has a `commits` row (idempotent through the primary key). A crashed full pass keeps the settled rule: purge, then a full re-mine.
4. `historyStale = (mined tip ≠ HEAD)`; the rewrite detector compares the mined tip with `HEAD` on the same ref (`--is-ancestor` exit 1 → `history_rewritten`; a different ref → `branch_changed`; any other status → git fault, no purge), as batch 4 settled.

Why this and not a skip-hash guard alone or a second `last_mined_head` row: a stream-position watermark is not an ancestry bound. Executed below, it both re-streams (`b..HEAD` → `d c2`) and loses commits under date skew (`b..HEAD` → `cc`, while `a`, b's parent, was streamed after `b` and is now excluded forever). A skip-hash guard makes re-streaming harmless but cannot recover a commit that was never streamed; a second row records the tip but leaves the range bound wrong. `--topo-order` removes the skew loss but not the re-stream (executed: the topo stream to M is `a b c2`, so the bound is `c2` and `c2..HEAD` after d re-streams `b`). Only a tip-keyed watermark is correct for both.
