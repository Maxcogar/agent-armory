### E-6
**Agree/Disagree:** Verdict — agree (replace). Reasoning — agree on the part-by-part reading against ruling 2: the `ts` cap is the settled design, the full-mine-only epoch 500 half-lives back is a partial step, the `> 1000` re-mine trigger is what ruling 2 drops, the 37-day floor lost its only derivation, and the silent underflow when `refTs` moves back is real. I reproduced it independently. Three corrections to the reasoning and one missed defect:
1. *The floor's criterion.* The first audit derives "about 1.16 days" from the subnormal limit (−1074) and sets it beside ruling 2's 1.79, which uses the normal limit (−1022). The two numbers answer different questions. The normal limit is the right criterion, because the weights are only read as ratios and a subnormal loses relative precision: `2**-1073.5 / 2**-1073` evaluates to 0.5, where the true ratio is 0.707. My derivation follows.
2. *The floor is a relation, not a constant.* `miner.horizon_years` (seed 5) is tunable, and `checkTuningWrite` has no relation on it. Every floor figure here, the plan's "about [450, 500]" included, holds only at Y = 5 years.
3. *The floor covers a fresh mine only.* The horizon is judged per pass, so an incrementally extended store keeps commits older than Y years. Under this design their terms are never rescaled, so they cannot underflow. Under ruling 2's rescale they do shrink with every advance, and they reach 0 about 1,074 half-lives after the commit (about 5.3 years at h = 1.79 days). A file whose every term has aged out then reads 0/0. The correction must state the read-side rule for a zero weight. It cannot rely on the floor.
4. *Missed:* the design caps `ts` at `refTs` because `%at` is "author-controlled, untrusted repository content". But `refTs` is `<head>`'s `%ct`, which any commit sets just as freely. Executed at `HEAD`: one commit whose committer time is 40000000000 at the tip horizon-excludes the whole history. The store ends with no files, no pairs and no fault. This is M3's untrusted-date class moved from `ts` to `refTs`. Neither the review, the plan, the first audit nor ruling 2's text addresses it.

*Floor derivation (mine).* Let Y be `miner.horizon_years` in years, d = 365.25 × 86400 s, and h the half-life in days. A horizon-included commit of a fresh full pass has `refTs − Y·d ≤ ts ≤ refTs`: the lower bound is the horizon rule and the upper bound is the cap.
- *This design*, E = refTs − 500·h·86400. The exponent is x = (ts − E)/(h·86400), so x ∈ [500 − 365.25·Y/h, 500]. 2^x is a normal double iff x ≥ −1022, that is h ≥ 365.25·Y/1522. At Y = 5 that is h ≥ 1.1999 days; the non-zero bound (x > −1075) is h > 1.1595.
- *Ruling 2's layout*, the epoch advanced in whole half-lives with refTs − h·86400 < E ≤ refTs. Here x ∈ [−365.25·Y/h, 1), and a normal double needs h ≥ 365.25·Y/1022. At Y = 5 that is h ≥ 1.787 days, the ruling's "about 1.79".
- So under either layout nothing needs 37. The floor is h ≥ 365.25·Y/(1022 + offset), with offset 500 here and 0 under ruling 2. It belongs in `checkTuningWrite` as a relation between `bar.recency_half_life_days` and `miner.horizon_years`, not as the constant 37.

### E-8
**Agree/Disagree:** Verdict — agree (keep). Reasoning — agree on the defect and the fix; one sentence is overstated. "A SHA-1 repository cannot emit a 64-hex `%H` or vice versa, so the extra read would change no outcome" holds for headers (a header is only accepted where git writes `%H`), but not for the trailer, which is commit-message text: in a SHA-1 repository a message carrying `This reverts commit <64 hex>.` is now labelled, where the review's object-format read would not label it. The difference is harmless — the label is a message-text heuristic that never checks the named hash exists, so a 40-hex trailer written by hand is labelled today too — but the stated reason for dropping the review's read is "no outcome changes", and the true reason is "the only outcome that changes is a hand-written trailer, which the rule already accepts in 40-hex form". The verdict does not depend on it.
**Evidence:**
- The defect and the fix, reproduced independently: a `--object-format=sha256` repository with two commits and a `git revert --no-edit` [[ran]] `git log -1 --format=%B | tail -2; git log -1 --format=%H | tr -d '\n' | wc -c` → `This reverts commit d85f45542a00703d97f803a918431e3a665598479d1ee862eb20a1aa10c9d2dc.` and `64`; [[ran]] `node mine.mjs f39769a <repo> s256f39769a` → `{"commitsSeen":0,"files":[],"pairs":[],"meta":[{"key":"last_mined_commit","value":"5fdfebf7…"},…],"faults":[{"code":"miner_unparsed_numstat",…` (nothing mined, watermark at `HEAD`); `node mine.mjs 6bbda1d <repo> s2566bbda1d` and `node mine.mjs HEAD <repo> s256HEAD` → `{"commitsSeen":3,"files":[{"path":"a","change_count":3,…` and, on the `6bbda1d` store, `SELECT label, count(*) n FROM labelled_touches GROUP BY label` → `[{"label":"revert","n":2}]` (the 64-hex trailer labels the revert).
