### E-1
**Units:** B8-55-8a234d6-docs/plans/plan-phase-a.md#h1
**Question:** The Step 14 builder added a `schema_meta.indexing_in_progress` flag the plan did not name, and asked a reviewer to decide whether the plan should name it. Seventeen seconds after the build commit, and ninety-three minutes before the review, the coordinator wrote it into the plan's key list as "confirmed".
**Facts:**
- The builder recorded it as a plan silence and handed the decision to a reviewer [[middleware/context-oracle/docs/implementation-log.md@177e59f:L1283-L1291]] "A reviewer should decide whether the plan names it."
- The builder's reason is that pass 1 commits each file's hash before the cross-file rows [[middleware/context-oracle/docs/implementation-log.md@177e59f:L1285-L1289]] "Pass 1 commits each file's `content_hash`. After that, a crash or a throw before the cross-file rows (edges, `symbol_refs`) are written would leave those files skipped as unchanged forever."
- The plan line records it as confirmed, without saying by whom [[middleware/context-oracle/docs/plans/plan-phase-a.md@8a234d6:L2126-L2131]] "named by the -- Step 14 builder, confirmed 2026-09-26"
- The plan line states an absolute guarantee [[middleware/context-oracle/docs/plans/plan-phase-a.md@8a234d6:L2128-L2130]] "a pass that finds it set runs as full, so a crash between the -- file-row chunks and the edge/symbol_refs chunks can never leave files"
- The review that followed found a gap in the same mechanism [[middleware/context-oracle/docs/reviews/2026-09-26-step-14-build-review.md@bfe8d3b:L274-L274]] "The gap is M5: it is set only when `pending` is non-empty, and `full` does not revisit `in_tree = 0` rows."
- Commit times: [[ran]] `git show -s --format='%h %cI' 177e59f 8a234d6 bfe8d3b` → `177e59f 2026-09-26T07:16:40+00:00`, `8a234d6 2026-09-26T07:16:57+00:00`, `bfe8d3b 2026-09-26T08:50:18+00:00`.
**Standard:** Brief test 5 ("It shows why this choice is better than the alternatives, not only that it works") and test 7 (the right party made it). A crash-consistency flag of this kind is the "dirty bit" pattern (an intent marker set before a multi-transaction update and cleared at its end, forcing a full re-derivation on restart). The alternative that removes the cause is to commit a file's change key only in the transaction that completes its derived rows, so a crash leaves the file looking changed.
**Reasoning:** (1) The problem is real: the builder's description matches the code's two-pass write, where pass 1 commits `content_hash` and pass 2 writes edges. (2) A flag forcing a full pass does repair it, and it matches AD-26's `mining_in_progress`, so the mechanism is sound engineering. (3) The plan line does not compare it with the alternative that removes the cause: writing each file's `content_hash` last, in the transaction that finishes that file's cross-file rows. That alternative costs no full re-parse after a crash. The full re-parse is cheap on this repository (3.8 s) but grows with repository size. (4) "confirmed 2026-09-26" names no party. The builder asked for a reviewer, and the coordinator wrote the confirmation 17 s after the build commit, before any review. It is not an owner claim, but it reads like one: an unnamed "confirmed" in a document governed by the ledger rules. (5) "can never leave files skipped as unchanged" is true only of files still present. The review's M5 then showed that stale rows of absent files survive a full pass.
**Alternatives:** (a) Keep the flag, say who adopted it ("adopted by the coordinator at `8a234d6`"), and add the comparison with a hash-last write. (b) Replace the flag with a hash-last write: pass 1 writes the row with a sentinel key and the final chunk writes the real key. The choice between (a) and (b) is an engineering call. Either one must be written down with its reason.
**Consequences:** The M5 fix (`221a1bc` h22, `7fdbd7e`) extends the flag to absent-only passes, so it builds on this decision. The key-list comment in migration `001` was not updated (the builder noted it). Under the schema-checksum ruling, adding it later changes a shipped migration file's checksum, so the listing belongs in the plan or in a new migration, never in an edit to `001`.
**Verdict:** replace — keep the mechanism, but name who adopted it (not an unattributed "confirmed"), bound the "can never" claim to present files, and record the comparison with committing the change key last.
**Would be wrong if:** A record showed a reviewer (not the coordinator) judged the plan silence before `8a234d6`, together with a written comparison with a hash-last write.

**Standard:** A cache is correct only when its key covers every input of the cached value. Build systems implement this as dependency tracking, recording the inputs actually read and rebuilding when any of them changes. The review names the rule in its S1 evidence [[middleware/context-oracle/docs/reviews/2026-09-26-step-14-build-review.md@bfe8d3b:L59-L60]] "A cache key must include every input of the cached value; the parse's inputs are the bytes **and** the frontend."

So AD-12's "covers every input" and the plan's "name exactly" were false when written, and the runs confirm it on the built resolvers. The failure is the one S2 named: a silently wrong edge set, with `index_head` equal to `HEAD`. (4) The read-time disappearance clause and the worklist are required by the rule but not pinned by any test (B2, B3 survive).
**Alternatives:** The root cause is that resolution results are cached without their inputs. Option (i): store, per importer, the resolution inputs the resolver consulted — the candidate paths it probed (repository paths, not specifiers, so AD-19's no-specifier storage stands) and the `package.json` it read. Re-resolve an importer when any recorded path appears, disappears, or changes content. Option (ii): re-parse every importer on any change of the present set or of any `package.json`. That is correct but costs up to a full parse per file creation. The chosen rules (a)/(b) are cheaper than both and wrong in the three cases shown. Rule (a) alone already re-parses every file with `unresolved_imports > 0` whenever any path appears, a cost the plan does not state. On this repository that is 60 files per new path, measured after a full index with the `HEAD` frontends: [[ran]] `node exp/mem.mjs <HEAD dist> /home/user/agent-armory` → `files with unresolved_imports > 0: 60`.
**Consequences:** T-14-6's S2 cases (E-21) test only the presence cases. Every genre that reads `import_edges`, `test_map`, `entry_score` or `symbol_refs` (Coupling, Consequence, Verification, Orientation) inherits the silent staleness. The h24 half (the final transaction writes `frontend_fingerprint` and `walk_errors`) is sound as a write-ordering rule and stands with its keys (E-16).
**Verdict:** replace — keep the fingerprint trigger, but restate S2 as dependency tracking of each importer's resolution inputs (probed candidate paths plus the `package.json` read), remove "covers every input" and "name exactly" until that holds, and add tests for the read-time disappearance and the worklist.
**Would be wrong if:** The three `s2gap.mjs` runs are not reproducible on a `HEAD` build, or a later step (15–19) re-resolves unchanged importers on those inputs by another mechanism.

**Reasoning:** (1) M1 was real. The build opened by path after an `lstat` and read with no byte bound. (2) Opening once with `O_NOFOLLOW | O_NONBLOCK` and judging the descriptor removes the race on the final component, and a FIFO cannot block.
