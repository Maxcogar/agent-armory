- [[ran]] `node col.mjs` (`node:sqlite`; `symbols(id, name, norm)` with `norm` = the in-house tokens joined by a space and a plain index; `symbol_tokens(token, symbol_id)` with a plain index; names `Foo::Bar`, `foo-bar`, `barista`, `getUserName`; prefix range `>= 'bar' AND < 'bar' || U+10FFFF` on each) → `column prefix range for "bar": ["barista"]` / `table  prefix range for "bar": ["Foo::Bar","foo-bar","barista"]` / `column LIKE %bar% plan: [ 'SCAN symbols' ]` / `table range plan: [ 'SEARCH symbol_tokens USING INDEX st (token>? - The settled ruling on this storage [[middleware/context-oracle/docs/reviews/2026-09-26-branch-audit-B5a-adjudication.md@HEAD:L157]] "Keep the one-tokenizer rule and store one row per token, as `0676431` did."
**Standard:** The brief's test 2–4 (backing that is real and supports this decision): an executed result. AD-23 forbids an O(store) scan on the event path (cited in the same AD-2 paragraph at `0676431` L369–L371: "a plain index on `symbols(name)` is not used by `LIKE` — a full scan, O(store), which AD-23 forbids on the event path"). **Reasoning:** (1) The flaw was real: reproduced, the indexed range on a single normalized column finds `barista` and misses `Foo::Bar` and `foo-bar`, two of the names AD-2 itself promises agree between the paths; the only column query that would find them (`LIKE '%bar%'`) is a `SCAN`, which SQLite documents (the wildcard-first rule) and AD-23 forbids. An FTS5-only design — the fallback exists for builds without FTS5, which is the case this path serves. Store tokens as a JSON array column with an expression index — SQLite indexes one expression value per row, so a per-token index still needs one row per token. The table is the standard relational answer (one indexed value per row).
**Consequences:** Depends on AD-4 listing the table (h3, E-2) and on the plan's Step 7 DAO and 001 DDL at `8162f00`, which already build it. Leaves B5a E-18's tokenizer-order correction where it was (lines 359–361 of the same paragraph), owed by a later architecture pass.
**Verdict:** keep — the raised flaw is real and reproduced; the table is the executed, standard fix; the settled ruling keeps it.
**Would be wrong if:** a plain index on one normalized column could serve a prefix query for a name's second token in SQLite (the reproduction shows it cannot), or B5a E-18 had ruled against one row per token.

(3) The `tune` notice stays, so the owner is told what will happen without being asked to do it. (4) The hunk's scope is exactly the rule and its storage; B5a E-19's settled correction names this hunk's rule as the form to keep.
**Alternatives:** Rescale at read — impossible on aggregate sums without per-commit timestamps per pair (the weights would need a per-commit table, a larger store and event-path work AD-23 forbids). Refuse the `tune` write until the owner runs a re-mine — puts the operation on the owner, the flaw being fixed. Store weights per commit and recompute — Phase A's data volume and AD-23 make the re-mine the cheaper and simpler consistent state. The chosen rule is the minimal one that keeps the invariant without owner action.
**Consequences:** Depends on AD-13's purge set (settled at `6cff0ce`; B5b's watermark rule changes when the watermark is written but not the purge or this trigger). The plan at `8162f00` Step 12 (`tuningWriteNotice`) and Step 13 already build it. Note for the correction pass: Step 12's notice at `8162f00` still quotes the superseded AD-13 sentence ("Changing `h` requires a re-mine, which `tune` states"), which this commit replaced — a plan-side stale quote, outside this unit.
**Verdict:** keep — the flaw is real (aggregate weights cannot be rescaled; the owner must not hold the invariant), the automatic purged re-mine is the settled and correct fix, and the hunk records the rule and its reason exactly.
**Would be wrong if:** the stored weights could be rescaled to a new `h` from the data the store keeps (they are sums over commits whose `ts` values are not kept per pair), or if a settled verdict had ruled against automatic re-mining (B4 and B5a E-19 rule for it).
