### E-11
**Agree/Disagree:** Verdict: **agree** (replace). Reasoning: **partly disagree.** The diagnosis is right:
- nested plan-mode sessions write into the shared `~/.claude/plans`, which this repo's root CLAUDE.md names as the handoff store;
- deleting by set difference over a window of up to 1200 s, with six sessions running in parallel, removes *any* file another process creates in that window;
- throwing away the nested sessions' plans discards evidence the measurement could use.

But the root-cause fix the first auditor prescribes is the wrong one, and it missed the documented, targeted one. It recommends a per-run `CLAUDE_CONFIG_DIR`. The authentication docs say that on Linux the login lives in `~/.claude/.credentials.json`, and under `CLAUDE_CONFIG_DIR` "Claude Code keeps the `.credentials.json` file under that directory instead". So a fresh config dir would start every nested session signed out, and would also drop the user settings the old/new comparison runs under. That would be a different, broken experiment. Claude Code has a dedicated setting for exactly this: `plansDirectory`. It chooses where plan mode writes plan files, is resolved relative to the project root (here, the throwaway clone), is allowed in any settings scope, and can be passed per session with `--settings`. With it, plans land in the clone, can be copied into `--out` as evidence before the clone is removed, and nothing touches the user's handoff store. The "would be wrong if" hedge in the first opinion (whether plans follow `CLAUDE_CONFIG_DIR`) is therefore moot. A further defect: when `~/.claude/plans` did not exist before the run, `before` is empty and every file that appears in the directory is deleted, including other sessions' files. And `os.remove` on a subdirectory raises inside the `finally`, which can abort the run before results are printed.
