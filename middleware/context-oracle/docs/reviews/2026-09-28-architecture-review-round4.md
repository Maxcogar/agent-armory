- **Hold measure: the proposed design** (R4-3's required change).
  1. *Two quantities, measured apart.* On every writer the fixture measures (the pass, a CLI migration, `import-human`), set `PRAGMA wal_autocheckpoint = 0`. Run `PRAGMA wal_checkpoint(PASSIVE)` in each yield gap, outside any write transaction. `BEGIN IMMEDIATE` returned → `COMMIT` returned is then the lock hold with no checkpoint inside it. Record it as `holdMs`, and record the gap checkpoint's duration and its `(busy, log, checkpointed)` result as `checkpointMs`. `write_hold_exceeded` compares `holdMs` only.
  2. *The event path, decided explicitly.* Either give handler connections `wal_autocheckpoint = 0` too, so no audit write runs a checkpoint while a pass runs. The last-connection-close checkpoint still runs when no pass holds the store; measure it. Or keep the default and list "a `COMMIT` may run a PASSIVE checkpoint of the WAL" in AD-23's inventory with its measured bound.
  3. *The waiter records three numbers per write:* time inside `BEGIN IMMEDIATE` (lock wait), time inside `COMMIT` (own commit plus any checkpoint it ran), and whether `onBusyRetry` fired.
  4. *Protocol.* A fresh copy of the seed store per run. At least 10 runs of each shape (rescale 20,000, reset 500, move 1,000), alone and beside the waiter, idle and under settlement (c)'s 3-spinner load. Report the maximum and p99 of `holdMs`, with every hold over 100 ms listed with its WAL frame count.
  5. *Then derive the bounds* from the `holdMs` distribution: max under 100 ms, p99 with margin.
  My pilot of item 1: move 1,000 held 58.4–61.9 ms and reset 500 held 56.6–58.6 ms alone, with the gap checkpoint's maximum 51.3–119.9 ms (E-3).
